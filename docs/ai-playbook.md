# Personal AI Coding Playbook

## When I reach for AI first

- When I need help understanding unfamiliar code, errors, or project structure.
- When I want a focused first draft for a small, clearly defined coding task.
- When I want a second set of eyes to review a plan, diff, test, or implementation.

## When I do not reach for AI

- When I have not yet understood the requirement or decided what I actually want to build.
- When the task involves sensitive information that should not be shared.
- When I can make a simple, well-understood change faster and more confidently myself.

## My non-negotiables

- I stay responsible for every change that enters the repository.
- I do not accept changes I cannot explain or verify.
- AI should respect the project's existing scope, architecture, and explicit constraints.

## My review rules

- I inspect the proposed change or diff before applying it.
- I run the relevant tests and verify the actual behavior rather than trusting the explanation.
- I prefer small, reversible changes and investigate unexpected edits before continuing.

## What I am still figuring out

- When AI saves enough time to justify using it instead of coding directly.
- How much context to provide without overwhelming the task.
- Which kinds of work benefit most from AI assistance and which are better handled manually.

## Decision Card

- For a new feature I reach for: **AI to help me plan, clarify requirements, and draft a small first version**
- For a code review I reach for: **AI as a second reviewer, while I make the final decision**
- For debugging I reach for: **AI after I collect the exact error, failing test, or unexpected behavior**
- For infrastructure I reach for: **AI cautiously, with explicit constraints and review before applying changes**
- I will never paste **passwords, API keys, secrets, or private credentials** into an AI tool.
- My one rule is: **I do not accept a change I cannot understand, review, and verify.**
